# Phase 13B booking identity package

Status: Implemented locally / Awaiting Independent Review. Phase 13B remains in progress. No booking creation, inventory, payment or frontend cutover is included.

Five accepted HTTP operations now run through the generated 46-operation identity protocol registry: guest challenge/verification, passenger ownership challenge/verification and claim. Every write verifies HTTPS, the exact configured Origin and raw session-bound CSRF. Guest challenge authority requires the anonymous passenger session; ownership requires a current active, verified passenger with usable Argon2id credentials. Unknown account/booking paths remain fail-closed. No guest fallback bypasses a bad cookie.

The server matches surname against persisted passengers and dispatches only to the booking's persisted contact email. A mismatch persists a ten-minute decoy without a booking FK or deliverable outbox. Real OTPs use a versioned HMAC with a separately configured pepper, never APP_KEY. Missing or malformed pepper configuration yields 503 before proof writes. Generate a separate local random value into the ignored environment; the example file contains no credential. This initial configuration retains one version; replacing it invalidates outstanding OTPs rather than silently using another secret. A deployment rotation procedure must retain needed old versions or explicitly revoke outstanding proofs.

OTP verification requires current booking epoch, exact requesting session/purpose, an unconsumed/unrevoked challenge, fewer than five failed attempts and an unexpired deadline. Both challenge and outbox must record provider acceptance, including its message ID and timestamp. Local capture is insufficient and cannot mint guest access. Tests inject explicitly synthetic persisted acceptance fixtures; no external mail provider or actual delivery is claimed. Failed attempts commit, including undelivered correct codes. Source-wide and per-reference/session rate budgets charge outside the domain transaction, so a rolled-back audit does not refund admission.

Guest tokens contain 32 random bytes, persist only their digest and eight exact approved actions, and expire after fifteen minutes. Ownership proofs expire after five minutes and bind the booking epoch, passenger and exact full session. Claim rejects foreign ownership with 409, consumes once, assigns an unowned booking and bumps its epoch/revokes preceding grants and proofs atomically. A self-claim consumes its proof as an honest ownership no-op. Authority reads refresh PostgreSQL time after lock acquisition. Lock order is passenger (where applicable), booking, session, challenge/proof, outbox. Lock and statement waits are bounded.

`BookingGrantAuthority` supplies transactional guest/receipt consumers for subsequent booking handlers, scoped to exact reference, action, epoch, revocation and maximum TTL. Its receipt issuance hook requires a trusted active booking transaction, stores a digest and permits only `getBookingReceipt` for ten minutes; no public mint endpoint exists. Checkout issuance and minimal itinerary projection remain Phase 13D domain integration. There is no receipt HTTP endpoint here, and no itinerary is fabricated. The ownership response exposes persisted contact/passengers and an empty legs collection because this inert identity dependency schema has no booking-leg authority yet; this must be replaced with persisted legs when the booking domain is implemented. This is not an operational booking-management implementation.

`BookingTransientCleanup` expires at most 100 total challenge/proof/grant records per cycle in the same hierarchy, including decoys. It retires metadata and erases expired challenge outbox ciphertext without deleting immutable audit or retained principals. The guarded manual local maintenance command invokes it. Scheduling and remote delivery remain deferred infrastructure gates.
