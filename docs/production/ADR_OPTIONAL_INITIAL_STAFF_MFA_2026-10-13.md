# Optional initial staff MFA — owner policy amendment, 2026-10-13

Status: source implementation for independent review; no deployment or production activation authorized by this change.

The owner explicitly requires verified invited staff to set their own password and enter Admin without compulsory authenticator enrollment. Initial MFA is an authenticated account-security choice. This supersedes the compulsory initial-enrollment portions of the Phase 12/13B identity policy and the H1/H2 enrollment-retry note. HostPapa PHP/MySQL remains the permanent runtime target.

A never-enrolled active staff account receives a rotated full staff session with `assurance=password` and an actual `password_verified_at`. Its MFA version and verification instant remain null. Accounts with any confirmed MFA history cannot fall back to password authority: enrolled sign-in still requires valid TOTP or a one-use recovery code against the current confirmed, unrevoked credential. No disable operation is introduced. Existing MFA proof timestamps are preserved by migration and rotation.

Initial setup is reachable in Admin Settings / Security for authenticated staff of every role. It requires the own current password, a full staff session and exact staff CSRF. Confirmation requires the same live session, epoch, unexpired five-minute pending-purpose token and fresh TOTP; failures consume the existing durable five-attempt budget. Successful enrollment revokes previous sessions and pending authority and rotates to a new MFA session. Existing enrolled users continue using the existing recent-factor replacement and recovery-code operations.

Sensitive operations preserve the five-minute same-session recent-auth rule: never-enrolled staff re-enter their password; enrolled staff provide TOTP or recovery. Rotation never refreshes either verification timestamp or the original absolute expiry. Role permissions, active/verified status, usable password, exact credential epoch, revocation and expiry are rechecked from current durable authority. The last-admin sentinel counts both legitimate eligible forms and still protects the final eligible administrator.

The additive MySQL migration replaces only the active-staff/MFA-only session checks, adds explicit assurance/password proof columns, and classifies existing full sessions as MFA without fabricating password proof. Rollback refuses to strand password-only active accounts or sessions and requires explicit remediation. Existing accepted migrations are unchanged. Review and execute migration before deploying code that selects the new fields.
